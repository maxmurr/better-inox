Integration Tests cover multiple components, hooks, and even some out-of-process
dependencies. That means they offer, by definition, more protection against
regressions than unit tests, given their inherently higher code coverage.

Let's use the same example as before — Creating a new quiz in our app.

During unit tests, we could only assert the output of the _createQuizModel()_
function. Here's an example:

```ts
import { createQuizModel } from './createQuizModel';

describe('createQuizModel', () => {
  it('creates a valid quiz model from user inputs', () => {
    const form = {
      title: '  JavaScript Basics  ',
      questions: [
        {
          heading: '  What is a closure?  ',
          imageUrl: '  https://example.com/img.jpg  ',
          type: 'single' as const,
          answers: ['  A function with preserved scope  ', '  A CSS feature  '],
        },
      ],
    };

    const result = createQuizModel(form);

    expect(result).toEqual({
      title: 'JavaScript Basics',
      questions: [
        {
          heading: 'What is a closure?',
          imageUrl: 'https://example.com/img.jpg',
          type: 'single',
          answers: [
            { id: '1', text: 'A function with preserved scope' },
            { id: '2', text: 'A CSS feature' },
          ],
        },
      ],
    });
  });
});
```

As we mentioned, this is a good unit test, but it doesn't guarantee any of the
following works as intended:

- Page navigation
- Form inputs
- Form buttons
- Data submission

That's precisely where (good) integration tests shine. They ensure that
everything is wired together well and that the user journey to create a new quiz
actually works.

Here's an example: _(integration test with Cypress for Nextjs app that use
server action)_

```ts
import { useCreateQuiz } from '@/features/quizzes/useCreateQuiz';
import { useRetrieveQuizzes } from '@/features/quizzes/useRetrieveQuizzes';

describe('Create Quiz', () => {
  it('creates a quiz successfully', () => {
    // --- Stub backend adapters (server action) ---
    // When form submits → server responds successfully
    cy.injectFakeAdapter(useCreateQuiz, {
      body: {
        id: 'QUICK_ID',
        title: 'JavaScript Basics',
        questionsCount: 1,
      },
    });

    // --- Start user journey ---
    cy.visit('/quizzes/create');

    // Fill quiz title
    cy.getByLabel('Quiz Title').type('JavaScript Basics');

    // Fill question 1
    cy.getByLabel('Question Heading').type('What is a closure?');

    cy.getByLabel('Image URL (Optional)').type(
      'https://example.com/closure.jpg'
    );

    cy.getByLabel('Question Type').select('Single Choice');

    // Add two answers
    cy.contains('Add Answer').click();
    cy.getByLabel('Enter answer')
      .eq(0)
      .type('A function with preserved lexical scope');

    cy.contains('Add Answer').click();
    cy.getByLabel('Enter answer').eq(1).type('A CSS feature');

    // Submit
    cy.contains('Create Quiz').click();

    // --- Assertions ---

    // Success message
    cy.contains('Quiz created successfully').should('be.visible');

    // Redirect to quizzes list
    cy.url().should('match', /\/quizzes$/);
  });
});
```

Note that this type of test, while providing a much higher protection, already
starts degrading the two other attributes we discussed before:

- Maintainability → Setting up an integration test requires more details and
  coordination
- Feedback Speed → Executing the UI takes way more time than in-memory function
  executions.
