A test's **feedback speed** is how fast it runs. Tests that use fewer resources
run faster, so they tell us sooner whether our implementation works. Tests that
rely on databases, user interfaces, or network calls take longer and can add
considerable time to CI runs.

We can now add feedback speed to our comparison:

```
|             | Maintainability             | Feedback Speed  |
|-------------|-----------------------------|-----------------|
| Unit        | High (= easy to maintain)   | High (= fast)   |
| Integration | Medium                      | Medium          |
| E2E         | Low (= hard to maintain)    | Low (= slow)    |
```

**Unit tests.** They score **high** because they usually run in memory without
out-of-process dependencies, frameworks such as React or Next.js, or a browser
and DOM.

**Integration tests.** They score **medium**. Although they stub out-of-process
dependencies, they still require a browser and DOM.

**E2E tests.** They score **low** because they start a browser and communicate
with external processes.

Unit tests may seem like the best investment because they score high in both
maintainability and feedback speed. Why write integration or end-to-end tests?

Their extra cost pays off in the next two attributes: **resistance to
refactoring** and **protection against regressions**.
