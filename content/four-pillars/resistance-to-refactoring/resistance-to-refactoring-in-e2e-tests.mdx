We finally got the last level of the test pyramid - End-to-end (E2E) tests. It's
worth noting that these types of tests are very similar in shape to the
integration tests (usually using the same tools and structure), but with much
heavier configuration and environment requirements since they rely on
production-like dependencies.

Let's recap an example of an e2e test for the quiz creation:

```ts
describe('Create Quiz', () => {
  it('creates a quiz successfully', () => {
    // --- Start user journey ---
    cy.visit('/quizzes/create');

    // Fill quiz title
    cy.getByLabel('Quiz Title').type('JavaScript Basics');

    // Fill question 1
    cy.getByLabel('Question Heading').type('What is a closure?');

    cy.getByLabel('Image URL (Optional)').type(
      'https://example.com/closure.jpg'
    );

    cy.getByLabel('Question Type').select('Single Choice');

    // Add two answers
    cy.contains('Add Answer').click();
    cy.getByLabel('Enter answer')
      .eq(0)
      .type('A function with preserved lexical scope');

    cy.contains('Add Answer').click();
    cy.getByLabel('Enter answer').eq(1).type('A CSS feature');

    // Submit
    cy.contains('Create Quiz').click();

    // --- Assertions ---

    // Success message
    cy.contains('Quiz created successfully').should('be.visible');

    // Redirect to quizzes list
    cy.url().should('match', /\/quizzes$/);

    // list shows our newly-created quiz
    cy.contains('JavaScript Basics').should('be.visible');
  });
});
```

As we mentioned, ensuring the API and any external dependencies (like Local
Storage) are up and running in the desired state can be complex, but this test
has the highest possible resistance to refactorings. Notice that it **will
pass** even if:

- We change the internal hook used to create the quiz
- We change the external API endpoint
- We change the internal Quiz model representation
