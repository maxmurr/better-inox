**Resistance to refactoring** measures whether a test keeps passing when we
change internal code without changing observable behavior:

- A use case has an existing test suite.
- We refactor its implementation.
- The test suite stays green.

Resistant tests avoid **false positives**.

> A false positive occurs when a test fails because an implementation detail
> changed, even though observable behavior stayed the same. Repeated false
> positives make teams trust the suite less, which raises the chance that they
> overlook a real bug.

To make tests **resistant to refactoring**, avoid coupling them to
implementation details. Brittle tests check internal steps instead of observable
behavior:

These tests depend on specific internal components or steps. Changing those
steps breaks the tests even when the use case still works.

Resistant tests check observable behavior instead:

<img
  src={'/images/four-pillars/resistant-test-case.png'}

These tests break when observable behavior changes, not when internal structure
changes. An unexpected failure is more likely to point to a real bug.
