Integration tests sit one level above unit tests in the test pyramid. Consider
this React hook:

```ts
// useCreateQuiz.ts
import { useState } from 'react';

import { createQuizModel } from './createQuizModel';
import { quizApi } from './quizApi';

export function useCreateQuiz() {
  const [isLoading, setIsLoading] = useState(false);

  async function submit(form: QuizForm) {
    setIsLoading(true);

    const model = createQuizModel(form);
    await quizApi.create(model);

    setIsLoading(false);
  }

  return {
    submit,
    isLoading,
  };
}
```

Testing this hook in isolation couples the test to its implementation. This unit
test shows the problem:

**Unit test:**

```ts
import { act, renderHook } from '@testing-library/react';

import { createQuizModel } from './createQuizModel';
import { quizApi } from './quizApi';
import { useCreateQuiz } from './useCreateQuiz';

jest.mock('./quizApi');
jest.mock('./createQuizModel');

describe('useCreateQuiz', () => {
  it('calls createQuizModel and toggles loading state', async () => {
    (createQuizModel as jest.Mock).mockReturnValue({ fake: 'model' });
    (quizApi.create as jest.Mock).mockResolvedValue(undefined);

    const { result } = renderHook(() => useCreateQuiz());

    expect(result.current.isLoading).toBe(false);

    await act(async () => {
      await result.current.submit({
        title: 'JS Basics',
        questions: [],
      });
    });

    expect(createQuizModel).toHaveBeenCalled();
    expect(quizApi.create).toHaveBeenCalledWith({ fake: 'model' });
    expect(result.current.isLoading).toBe(false);
  });
});
```

Although this test is easy to set up, it fails after any of these changes, even
when observable behavior stays the same:

- Inline _createQuizModel()_ into the hook
- Rename or remove _createQuizModel()_
- Replace _useState()_ with _useTransition()_
- Move loading state handling elsewhere
- Change how the payload is assembled internally

From the user's perspective, nothing changed:

- The quiz is still created.
- The UI still shows a loading state.
- The app still makes the same API call.
- The user sees the same result.

The test breaks because its **mocks** expose implementation details. Mocks can
be useful at observable system boundaries, but mocking collaborators inside the
hook couples the test to its internal steps. Instead of unit-testing this hook,
test its behavior through an integration test:

**Integration test:**

```ts
import { useCreateQuiz } from '@/features/quizzes/useCreateQuiz';
import { useRetrieveQuizzes } from '@/features/quizzes/useRetrieveQuizzes';

describe('Create Quiz integration', () => {
  it('creates a quiz successfully', () => {
    // --- Fake backend adapters (observable boundary) ---
    cy.injectFakeAdapter(useCreateQuiz, {
      body: {
        id: 'quiz-123',
        title: 'JS Basics',
        questionsCount: 0,
      },
    });
    cy.injectFakeAdapter(useRetrieveQuizzes, {
      body: [
        {
          id: 'quiz-123',
          title: 'JS Basics',
          questionsCount: 0,
        },
      ],
    });

    // --- Start user journey ---
    cy.visit('/quizzes/create');
    cy.getByLabel('Quiz Title').type('JS Basics');
    cy.contains('Create Quiz').click();

    // --- Assertions (observable behavior only) ---
    cy.contains('Quiz created successfully').should('be.visible');
    cy.url().should('match', /\/quizzes$/);
    cy.contains('JS Basics').should('be.visible');
  });
});
```

This test does not depend on:

- Whether _createQuizModel()_ exists
- How the hook builds the payload
- How the loading state is implemented
- Whether the hook uses _useState_, _useReducer_, or _useTransition_
- Whether the API call lives in the hook or in a service

You can refactor all of those details. The test keeps passing as long as the
user can:

- Fill out the form
- Click "Create Quiz"
- See a success message
- Reach the quiz list
- See the new quiz
