People use "refactoring" to mean different things, from any code change to a
risky cleanup. Martin Fowler's book
[Refactoring](https://martinfowler.com/books/refactoring.html) gives us a more
precise definition:

<img
  src={'/images/four-pillars/refactoring-book-cover.jpg'}
  alt={
    'Cover of Refactoring: Improving the Design of Existing Code, second edition, by Martin Fowler with contributions by Kent Beck, from the Addison-Wesley Signature Series.'
  }
  width={434}
  height={522}
/>

The preface defines **refactoring** this way:

> _Refactoring is the process of changing a software system in a way that does
> not alter the external behavior of the code yet improves the internal
> structure. It is a disciplined way to clean up code that minimizes the chance
> of introducing bugs._
>
> Martin Fowler

This definition makes two points:

1. External, observable behavior must not change.
2. Refactoring should reduce the chance of introducing bugs.

To understand the first point, think of software as a system that receives an
**input**, processes it, and returns an **output**:

<img
  src={'/images/four-pillars/input-impl-output.png'}
  alt={
    'Hand-drawn diagram: an Input circle points into a dashed box holding red, blue, and green circles connected by arrows, which points out to an Output circle.'
  }
  width={1192}
  height={749}
/>

**Observable behavior** is what a user or client can measure. Inputs and outputs
are observable. The internal steps that transform one into the other are
**implementation details**:

<img
  src={'/images/four-pillars/observable-behavior.png'}
  alt={
    'The same Input to Output diagram with the dashed box titled Impl. Detail, orange braces under the Input and Output circles labelled O.B, and a legend reading O.B = Observable Behavior.'
  }
  width={1192}
  height={749}
/>

Refactoring changes those implementation details while preserving the same
relationship between inputs and outputs. The next lesson gives examples.
